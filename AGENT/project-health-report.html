1. Open findings

UX-1 low index.html:26–39

No failure feedback; the fetch has no catch. Two failure modes leave the visitor without any signal. A network/DNS error (or a failed res.json()) rejects the promise chain, so the initial “Loading…” text stays on screen forever. A rate-limited response (the unauthenticated GitHub API allows only ~60 requests/hour per IP) returns a JSON object, not an array; list.textContent is cleared first and then for (const repo of repos) throws an unhandled TypeError, leaving a blank list plus a console error.

Recommendation: add a .catch (and an Array.isArray(repos) guard) that replaces the list text with a short “couldn’t load projects” message — one line that turns both silent failures into honest feedback.

UX-2 low index.html:29–38

Empty result renders a blank page. When no repo has has_pages set, the loop appends nothing after list.textContent is cleared, so the visitor is left with just the heading and an empty list — no “no projects” message. (Not triggered today: the account has four live Pages sites.)

Recommendation: after the loop, if the list is still empty, append a single fallback line such as “No projects yet.”

A11Y-1 low index.html:18

Async list update is not announced. The <ul id="projects"> starts as “Loading…” and is populated later, but it carries no aria-live, so a screen-reader user who has already focused the region is not told when the links appear. (The links remain reachable by normal navigation afterward.)

Recommendation: add aria-live="polite" to the list — a single attribute, no code cost.

DOC-1 info CLAUDE.md · Conventions

Convention references a field that is no longer rendered. The textContent-not-innerHTML convention is still correct and followed, but it is phrased around repository descriptions, which the minimal page no longer displays. The untrusted value now inserted into the DOM is the repository name.

Recommendation: reword the convention to speak of untrusted GitHub API data / repository names (fix via create-claude-md or a small manual edit).

2. What is already strong

  • Does one thing. Fetch the repos, keep the ones with has_pages, list them as links. No caching, images, theming or error UI to go wrong — the whole script is a dozen lines.
  • Single-request data flow. One call to the repos API, filtered by the has_pages flag — no per-repo HEAD probes, so there is no fan-out to fail.
  • HTML-injection safe rendering. The untrusted repo name is inserted via textContent and DOM APIs, never innerHTML — matching the documented convention.
  • Defensive headers. A tight Content-Security-Policy (default-src 'none') locks sources down to the API and a data: favicon; lang="en" and a viewport meta are set.
  • Zero dependencies, no build step, no comments. One self-contained index.html of short, clearly named code that reads on its own.

3. Deliberately decided

  • No caching, no styling, no error UI. Removed on purpose to keep the page truly minimal; browser default styling is accepted. The one caveat is the failure state this leaves behind — see UX-1.
  • has_pages instead of live probing. The list trusts the API’s has_pages flag rather than fetching each candidate URL. A repo with Pages enabled but a failed build could still be listed — an accepted trade-off for the simpler, single request.
  • No pagination. per_page=100 covers a personal account with wide margin; following the Link header would be added complexity for a case that does not occur.
  • Unauthenticated GitHub API. A public static page cannot embed a secret token, so the low anonymous rate limit is an accepted trade-off.
  • No framework / toolchain / tests. For a single static page this is a reasonable simplicity choice; no test harness is expected here.
