1. Open findings

UX-1 medium index.html · <head>

No viewport meta tag → not mobile-responsive. The page declares a responsive grid (minmax(440px, 1fr)) and the README claims the layout “adapts to the viewport,” but without <meta name="viewport"> mobile browsers render at a virtual desktop width and zoom the whole page out. Cards become tiny and text hard to read on phones; media queries behave against the layout viewport rather than the device width.

Recommendation: add <meta name="viewport" content="width=device-width, initial-scale=1"> in the head. Consider lowering the grid min column from 440px so a single card fits a narrow screen without horizontal scroll.

BUG-1 medium index.html:159–161

Unguarded JSON.parse(cached) can brick the whole page. The startup IIFE calls JSON.parse(localStorage.getItem(CACHE_KEY)) without a try/catch. If the cached value is malformed (partial write, storage tampering, format change across versions), the exception propagates out of the async IIFE and aborts initialization entirely, so the fresh fetch never runs and the visitor is stuck on “Loading projects…” forever.

Recommendation: wrap the parse in try/catch; on failure ignore the cache (and optionally localStorage.removeItem it) and fall through to the live fetch.

BUG-2 medium index.html:83–113

Transient network failures poison the cache. pageExists() returns false on any thrown error (timeout, DNS blip, offline). A project whose HEAD check momentarily fails is dropped from the rendered list and the result is unconditionally written back to localStorage (line 113). So a temporary hiccup silently removes a live project from the cache, and the next visit’s instant render shows the reduced set until a fully successful check restores it.

Recommendation: distinguish “404 / not a Pages site” from “request failed”; only overwrite the cache when the repo list actually loaded, and avoid dropping a previously-known-live project on a single failed check (e.g. keep prior entries or skip the cache write on error).

UX-2 medium index.html:92–95, 116–119, 167–169

API errors are indistinguishable from “no projects.” The unauthenticated GitHub API allows only ~60 requests/hour per IP. When the repos request is rate-limited it returns a JSON error object, not an array; repos.filter then throws, is swallowed by the outer catch, and fetchPagesRepos returns []. With no cache present the visitor sees the misleading message “No active GitHub Pages projects found.” instead of an error/retry hint.

Recommendation: check res.ok / Array.isArray(repos) before filtering and surface a distinct “couldn’t load projects, try again later” state separate from the genuinely-empty case.

SEC-1 low index.html · <head>

No Content-Security-Policy. The page has no CSP meta tag. Since all script is inline and only two external hosts are contacted (api.github.com, *.githubusercontent/opengraphgithubassets.com, plus *.github.io HEAD checks), a restrictive policy is cheap defense in depth against injected content.

Recommendation: add a <meta http-equiv="Content-Security-Policy"> limiting default-src 'none', img-src to the GitHub asset hosts, connect-src to the API/Pages hosts, and allowing the inline style/script only as strictly as feasible.

A11Y-1 low index.html:76

Results region is not announced to assistive tech. The #projects container starts as “Loading projects…” and is replaced later via textContent, but it has no aria-live, so screen-reader users get no notification when the loading text becomes the project list (or an empty/error message).

Recommendation: add aria-live="polite" (and consider role="status" for the transient text) to the container, or move the status text into a dedicated live region.

UX-3 low index.html:137–139

No fallback for broken preview images. Each card’s <img> points at opengraphgithubassets.com/1/…. If that request fails or a repo has no Open Graph image, the card shows a broken-image icon over its fixed 240 px area with no graceful degradation.

Recommendation: add an onerror handler that hides the image or swaps in a neutral placeholder, so the card still reads cleanly with just name and description.

META-1 info index.html:92–94 · <head>

Minor polish: pagination cap, SEO/meta, favicon. The repos fetch uses per_page=100 with no pagination, so accounts with more than 100 repositories would silently miss the rest. The head also lacks a <meta name="description"> and there is no favicon — small SEO/branding gaps for a public landing page.

Recommendation: follow the Link pagination header if the repo count may exceed 100 (currently unlikely), and add a page description and a favicon.

2. What is already strong

  • HTML-injection safe rendering. Untrusted repo names and descriptions are inserted via textContent and DOM APIs, never innerHTML — matching the documented convention and closing the previously reported injection risk.
  • Instant perceived load. Cached results render immediately on startup before the network round-trips complete.
  • Parallel liveness checks. The candidate HEAD requests run concurrently via Promise.all, keeping the refresh fast.
  • Light/dark theming. Clean CSS-variable theming driven by prefers-color-scheme, including a dark-mode description color.
  • Zero dependencies, no build step. The whole site is one self-contained index.html — easy to audit and deploy.
  • Housekeeping. lang="en" is set, images carry alt text, an SPDX license identifier is present, and README/CHANGELOG/CLAUDE.md are consistent with the current code.

3. Deliberately decided

  • Everything inline in index.html. Markup, CSS and JS live in one file by design (documented in CLAUDE.md); not treated as a finding.
  • Unauthenticated GitHub API. A public static page cannot embed a secret token, so the low anonymous rate limit is an accepted trade-off. (The UX around hitting that limit is still worth improving — see UX-2.)
  • No framework / toolchain / tests. For a single static page this is a reasonable simplicity choice; no test harness is expected here.
